Cap connections in the payments client

PR #1290

Problem

Payments client opens unlimited sockets → file descriptors run out under retries.

Task

  • Limit the connection pool
  • Add backoff to retries
  • Keep payment semantics unchanged

Context

  • C1
    src/payments/client.ts
  • C2
    payments-client pool options
  • C3
    Root cause analysis (ACME-412)

Conclusions

  • 50 connections per pod covers peak with 2× headroom: peak is ~22 concurrent payment calls per pod.

    Based on
    C3
    Confidence
    medium

Assumptions

  • Idempotency keys are already sent on every retry, so backoff cannot create duplicate charges.

    Why assumed

    The code path sets the key, but I did not see it in provider logs.

    How to verify

    Check one retried request in the provider dashboard for the same idempotency key.

    Risk if wrong
    high

Result

PR #1290 ready:

  • pool cap
  • jittered exponential backoff
  • pool saturation metric
  • changed
    maxConnections: 50, queueTimeout: 2s in the client factory. client.ts
  • added
    Backoff 100 ms → 1.6 s with full jitter, 4 attempts max.
  • added
    Metric payments_pool_in_use.
  • verified
    Unit tests pass; the load test from ACME-412 passes with this branch.
