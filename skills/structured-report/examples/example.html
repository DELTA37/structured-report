Find why checkout p95 doubled after 2.14

ACME-412

Problem

Since
release 2.14, Nov 2 14:05
Latency
checkout p95 820 ms → 1.7 s
Timeouts
0.9% of payment attempts
Customers
charged without an order (support reports)

Task

  • Find the root cause with evidence
  • Say what to change to get p95 back to the pre-2.14 level

Context

  • C1
    Checkout latency dashboard, Oct 26 – Nov 4

    p95 jumps at 14:05 on Nov 2, the deploy time of 2.14.

  • C2
    2.14 diff: payments client upgraded 3.2 → 4.0
  • C3
    payments-client 4.0 changelog

    "maxConnections now defaults to unlimited".

  • C4
    Pod logs during the peak, 2026-11-03 19:00–19:30

    3,140 × EMFILE: too many open files, all from the payments client.

  • C5
    Support thread about double charges
  • C6
    src/payments/client.ts

Conclusions

  • The regression starts exactly with the 2.14 deploy, so it is caused by a change inside 2.14, not by traffic.

    Based on
    C1C2
    Confidence
    high

  • The payments client opens a new socket per retry and never caps them; under retries the pod runs out of file descriptors.

    Based on
    C3C4C6
    Confidence
    high

  • Double charges happen when the provider accepts a payment but our side times out before writing the order.

    Based on
    C4C5
    Confidence
    medium

Assumptions

  • The provider itself was healthy during the incident.

    Why assumed

    Their status page shows no incident, but we have no provider-side metrics.

    How to verify

    Ask the provider for request logs for Nov 3, 19:00–19:30.

    Risk if wrong
    medium

Result

Root cause
unbounded connections in payments client 4.0
Confirmed by
load test at 3× peak
  • decision
    Cap the pool at 50 connections per pod and add jittered backoff.
  • verified
    Load test with the cap: no EMFILE errors at 3× peak traffic. load test #77
    How: k6 run load/checkout.js --vus 300 — run #77
  • metric
    780 msp95 in the load test with the cap (was 1.7 s)
  • doc
    Incident timeline written up. timeline

Not checked

  • Provider-side metrics during the incident

    Why not

    No access — requested in Your actions

Cap connections in the payments client

PR #1290

Problem

Payments client opens unlimited sockets → file descriptors run out under retries.

Task

  • Limit the connection pool
  • Add backoff to retries
  • Keep payment semantics unchanged

Context

  • C1
    src/payments/client.ts
  • C2
    payments-client pool options
  • C3
    Root cause analysis (ACME-412)

Conclusions

  • 50 connections per pod covers peak with 2× headroom: peak is ~22 concurrent payment calls per pod.

    Based on
    C3
    Confidence
    medium

Assumptions

  • Idempotency keys are already sent on every retry, so backoff cannot create duplicate charges.

    Why assumed

    The code path sets the key, but I did not see it in provider logs.

    How to verify

    Check one retried request in the provider dashboard for the same idempotency key.

    Risk if wrong
    high

Result

PR #1290 ready:

  • pool cap
  • jittered exponential backoff
  • pool saturation metric
  • changed
    maxConnections: 50, queueTimeout: 2s in the client factory. client.ts
  • added
    Backoff 100 ms → 1.6 s with full jitter, 4 attempts max.
  • added
    Metric payments_pool_in_use.
  • verified
    Unit tests pass; the load test from ACME-412 passes with this branch.
    How: npm test + load test — CI #4120

Not checked

  • Pool behaviour when DNS fails

    Why not

    No environment to simulate it
